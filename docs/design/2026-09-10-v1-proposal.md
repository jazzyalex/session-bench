# Session-Bench v1 proposal

Status: draft for user approval. Prepared 2026-09-10 against repository commit `49b7c0a`. This document proposes work; it is not a new rubric, implementation, collection result, or release. The ongoing goal remains active beyond this design phase. Companion documents: [evidence and roadmap](2026-09-10-evidence-and-roadmap.md), [coverage and related work](2026-09-10-coverage-and-sources.md).

The question is: **How much of an agent's work can an independent tool faithfully reconstruct from the record it leaves behind?**

Build a public format atlas and executable session-conformance suite together. Keep continuation across different agents as a later experimental track because its success depends on model behavior as well as record quality. Preserve the current v0.4 data, evaluator, methodology, correction history, and citation metadata as a historical edition.

## Decision summary

| Decision | Recommendation | Reason |
|---|---|---|
| Product | Atlas + native-record conformance | Reference material attracts consumers; executable contracts make the project useful in their workflows. |
| Comparison | Tested surface/configuration, linked to artifact family | Shared schemas do not prove shared writer, retention, or discovery behavior. |
| Initial platform | macOS pilot, explicit OS label | Desktop automation and artifact layouts are platform-specific; no implied Windows/Linux coverage. |
| Evidence | Synthetic live-produced native records plus independent observations | Public reproduction cannot depend on private personal histories. |
| Scoring | Six mandatory core scenario families, optional profiles, category metrics | No universal weighted winner during v1; incomplete testing cannot improve a percentage. |
| Independence | Separate representability, writer, decoder, and reproduction claims | Prevent a decoder limitation or an unexercised operation from becoming a format failure. |
| Rollout | Offline prototype, small live calibration, eight-surface pilot, external reproduction | Validate measurement before paying to scale it. |
| Publication | Immutable results and corrections, stable result identifiers | Research and downstream tooling must be able to reference a fixed claim. |

## Current baseline and reusable assets

The repository has ten CLI/headless harness rows, twenty scored gates, an additional untested crash gate, four computed signal gates, and sixteen other scored checklist gates. All ten current rows have missing measurements and provisional rankings. The source contains 24 test functions: 11 evaluator tests and 13 measurement tests. This design pass inspected the tests but did not execute them.

Evidence anchors:

- [README](../../README.md): current rows, missing-data caveats, standalone workflow, and historical relationship to Agent Sessions.
- [Methodology](../../methodology.md): gates, rank rules, and the one-prompt probe.
- [Evaluator](../../scripts/evaluate.py): threshold computation, checklist validation, hard-coded harness registry, generated output, and rank ranges.
- [Measurements](../../data/measurements.json): private probe provenance, mixed corpus/measurement dates, and missing physical SQLite probe measurement.
- [Evidence limits](../../evidence/README.md): underlying raw artifacts and corpus transcripts are not public.
- [S4 receipt](../../evidence/receipts-2026-08-22-s4.md): contributed measurements without artifact hashes; filtered-row denominator and byte-count caveats are disclosed.
- [Backlog](../../BACKLOG.md): useful harness/surface/artifact distinction, paired probes, local-only boundary, and companion-store requirements.

Preserve deterministic generation, input validation, exact-fraction comparisons for the historical edition, receipt-query tests, extraction byte accounting, correction history, and provenance metadata. Reuse implementation only after testing its specific contract. Do not transplant the current rank formula or content-key heuristic into the new primary metrics.

The main limitation is observation reproducibility, not arithmetic reproducibility. Existing unit tests cannot establish that a live product preserved its work. The generic JSONL extractor silently skips malformed records in semantic counts, while retaining them in its line count; v1 needs explicit diagnostics. Existing SQLite measurements need a defined capture/snapshot contract before physical footprint and live consistency claims. The comment that read-only SQLite cannot see WAL rows conflicts with the adjacent WAL test; v1 must define supported capture behavior rather than inherit that comment.

The present rubric also embeds architectural preferences. Single-file tailing, no sidecars, plaintext containers, embedded dollar figures, and naive linear replay should become descriptive properties or outcome-based tests. Stable joins can be good; a documented binary decoder can be usable; a migration can improve storage while preserving old records. Rationale visibility is descriptive, not proof of actual cognition.

## Scope and identity

Native local persistence is the primary track. Explicit vendor exports are a separate track with acquisition steps, authentication requirements, omissions, and export version recorded. Network telemetry can supply independent observations when authorized, but cannot silently replace missing native records. Cloud-only products may receive atlas entries and an explicit local-availability result; they do not qualify as tested native-local implementations through an export.

A result identity contains:

`protocol version + scenario version + harness distribution/build + surface + launch mode + OS/build + model/provider/configuration + persistence settings + adapter version + decoder version + run ID`.

Distinguish the writer's application version from a format/schema version. A missing schema version remains `unknown`; it does not erase the known writer version. Record launch evidence and the exact executable/app identity. Do not infer the originating surface from a shared directory.

The atlas links each surface to one or more artifact families. A manifest lists root roles, physical encoding/tables, session identifiers, joins, attachments, subagent stores, metadata, retention, and acquisition method. A diagnostic log becomes part of the required bundle if it contains unique in-scope session information; classification follows function, not filename. Unrelated caches and credentials remain outside collection. Local-only scope does not grant access to existing personal stores.

Reuse format documentation and decoder fixtures when schemas genuinely match. Retain separate live-writer evidence for each surface and mode. If identical content is stored in multiple locations, keep the physical artifacts and evaluate logical deduplication explicitly.

## Claims and states

Every assertion declares one of four subjects:

| Subject | Permitted claim | Required evidence |
|---|---|---|
| Representability | Format can encode a feature | Public schema/source or labeled constructed fixture; not proof the product writes it. |
| Writer behavior | Tested build preserved a particular observed event | Native live-produced bundle plus independent observation of that event. |
| Decoder correctness | This decoder reconstructs expected content/relationships | Public fixtures, precise expected outputs, and source-record locators. |
| Reproduction | Another execution or implementation agrees | Separate attestation identifying what was repeated and by whom. |

Use separate axes rather than one overloaded verdict:

- Execution: `valid`, `not_run`, `invalid`, `not_exercised`. Include a reason code and all attempts.
- Applicability: `required`, `optional_supported`, `unsupported`, `unknown`. Unsupported requires evidence; failed access is not unsupported.
- Assertion: `pass`, `fail`, `unresolved`. A failure names its subject; uncertainty about decoder versus writer is unresolved at writer level.
- Evidence: `submitted`, `maintainer_verified`, `independently_recomputed`, `independently_reproduced`. Recomputing the same bundle and rerunning the live scenario are different achievements.

A feature absent from a native artifact does not automatically establish writer failure: first prove the event happened, check the full declared bundle, and independently validate the decoder interpretation. Conversely, product data loss after a valid trigger remains a failure even if the product later errors. An infrastructure/auth failure before exercising the trigger is invalid or not run. Retain all such attempts, not only successes.

Six core scenario families define fixed coverage. Unsupported or unresolved required capabilities leave core conformance incomplete; they do not shrink the required set. Optional unsupported capabilities are visible and cannot increase a core percentage. A fully verified failing result is still publishable: verification measures evidence quality, not product quality. `Core conformant` requires every mandatory assertion to pass across the declared repeat policy; use no blended score to compensate for lost work. Always publish the diagnostic matrix and per-event counts alongside that strict designation, including independently verified successes in incomplete results. Unsupported classification requires pinned product/version capability evidence and a documented trigger inspection; lack of search results or a model refusal is insufficient.

## Independent observation and normalization

Use a deterministic local fixture project with innocuous files, unique per-run markers, a controlled tool helper, and externally recorded interactions. Expected data is created before decoding and is never inferred from the native output being evaluated.

The observer records submitted/accepted user interactions, controlled helper invocations/results, file changes, and lifecycle triggers. Each observation has its own ID, origin, monotonic sequence, timestamp precision, and acquisition evidence. Desktop actions require actual UI execution evidence; launching a CLI in a desktop terminal does not test the desktop surface. Record human interventions and do not silently replace difficult UI steps with headless equivalents.

Permitted assistant-content observations are a captured live stdout/PTY display stream for the exact CLI mode, or accessibility text accompanied by UI screenshots/recording for desktop. Reading saved history, a transcript export, or a history endpoint that loads the same stored artifact is not independent truth. An independently tapped live response stream may supplement observation only when authorized, with its relationship to displayed content documented. Core C01 evaluates final visible assistant message blocks, including refusals and visible errors, with `completed`, `interrupted`, or `error` status; intermediate token deltas belong to an optional streaming profile. If a turn has several visible blocks, all independently captured blocks enter the population. No assistant output is a recorded fact, not an invented empty response. OCR-only extraction without reviewed uncertainty cannot support exact-text claims. Observer and decoder must be separate modules; disclose shared code, identifiers, and writer-supplied metadata so common failure sources are visible.

Measure only what the observer can establish. A helper invocation proves that helper action, not every uninstrumented built-in tool or hidden internal model request. Record visibility by event class. When a surface cannot supply independent observation of assistant content, relevant completeness assertions remain unresolved; do not infer omitted responses from the same transcript. Model IDs and token quantities need an independent source before accuracy claims; otherwise test availability and internal consistency only.

The normalized representation is a comparison view, not a required vendor format. It contains sessions, messages, tool attempts/results, lifecycle boundaries, relationships, usage observations, attachments, and explicit unknowns. Every item maps back to native evidence. Distinguish `absent`, `unknown`, `redacted`, `truncated`, and `not_observed`; never coerce them into empty text or zero.

Preserve native timestamps separately from observer timestamps. Use partial-order constraints for concurrent work; do not invent a total order or equate file order with causality. Preserve active/abandoned branches, summaries, and original records separately. Unknown native event types remain accounted for and visible in coverage diagnostics.

## Core scenario specifications

These are proposed contracts for calibration, not currently executed tests. C01-C05 each have three independent runs per tested surface. C06 has three conditions with three runs each, described below. Later rows cannot reuse runs from another surface.

| ID | Trigger and independent truth | Required assertions | Invalid/unexercised boundary |
|---|---|---|---|
| C01 Conversation | Submit three short turns including a correction; capture accepted text and visible completed responses independently. | Accepted user content, observed response content, roles, turn order, and distinct IDs reconstruct without duplicates. Preserve correction as history. | Prompt not accepted or observer missed a response; never demand a particular generated answer. |
| C02 Tools and attempts | Request controlled helper calls: one success, one intentional failure, then success; helper separately records arguments, output bytes, exit status, and attempt IDs. | All observed helper attempts pair with correct results and ordering; failure cannot become success or disappear. | Agent never invokes helper = not exercised; helper observer fails = invalid; product omission after execution = eligible failure. |
| C03 Restart and resume | Complete known turns/tool events, freeze the target locator from ID plus creation marker before closing, enumerate after reopening, select that session and submit a continuation. | Prior observed history remains independently readable; resumed lineage is explicit and no duplicate logical turns appear. Record continuation behavior separately. | Operator selection error is invalid only if the predeclared locator was unambiguous; product ambiguity is measured. No supported resume leaves required family incomplete. No requirement that model recall every earlier fact. |
| C04 Discovery and copied bundle | Create two sessions in the fixture project; capture root changes; copy declared bundle into an offline reader workspace. | Enumerate both, attribute fixture project, resolve required joins, reconstruct prior observed content without vendor backend/UI or accidental access to original paths. | Capture cannot establish coherent snapshot = invalid. No durable local record is an observed limitation, not a successful empty bundle. |
| C05 Cancellation | Start a controlled long operation, observe its start, cancel through the tested surface, then continue if supported. | Previously completed work remains; pending work is not falsely marked completed; cancellation/incompleteness is explicit; later work is linked correctly. | Operation completed before trigger = not exercised; UI trigger unconfirmed = invalid. No assertion that cancellation undoes filesystem side effects. |
| C06 Process-termination recovery | Observe completed markers; terminate the declared persistence process set at a quiet-period barrier, tool-start barrier, or tool-result barrier; freeze post-termination evidence before reopening. | Require recovery of the settled completed prefix and truthful incomplete-state handling. Separately report immediate recent-event loss and any explicitly acknowledged-persistence loss. | Wrong process killed or observer/capture failed = invalid. Data loss after a valid trigger remains an outcome. No inference of vendor flush acknowledgement from visible completion. |

For C06 use three separately reported conditions, each repeated three times: (A) after a fixed quiet interval following the final visible response, (B) after a new controlled helper starts, and (C) after that helper emits its result. All conditions begin with the same independently observed prefix followed by the fixed quiet interval. The proposed interval is 2 seconds, subject to public calibration and freezing before scored collection; it is a benchmark user-outcome threshold, not a vendor durability promise. No per-product tuning. Core assertions concern recovery of that settled prefix and absence of fabricated completion; immediate events at B/C yield diagnostic loss-window measurements, not unsupported claims about flush guarantees. If the product exposes independently observable persistence acknowledgements, report an additional acknowledged-event loss assertion separately. Missing acknowledgement is explicitly unknown and does not improve a score.

Predeclare executable paths/builds and the persistence process tree or daemon set, termination mechanism/signal, supervisor relationship, auto-relaunch controls, and post-kill liveness check. Kill only isolated benchmark processes. If the persistence process cannot be identified or recovery cannot be stopped before capture, the condition is invalid. Use a helper/controller handshake for B/C, record monotonic trigger and termination times, and publish the observed timing window. Events whose relative order is ambiguous within that window are unresolved for immediate-loss metrics. Capture the full declared artifact set before recovery, including present WAL/journal companions. This measures controlled process-termination recovery, not power-loss durability or a probability of safety under arbitrary crashes.

## Optional profiles

| Profile | Scenario and assertions |
|---|---|
| Branches and collaboration | Fork/rewind, two concurrent helpers, two subagents, and side thread. Match independently triggered identities; reconstruct parent/child and active branch; preserve abandoned paths without merging them. No inference of links from titles alone when testing explicit attribution. |
| Compaction | Trigger supported compaction after known markers. Test archival preservation separately from effective resumed context. Identify summary boundary, lineage, and documented omissions; do not demand preservation of hidden model state. |
| Attachments and large outputs | Supply a synthetic image/file and controlled large output. Check payload or stable resolvable reference, content hashes, truncation markers, and dependencies. Do not demand identical image encoding. |
| Orphan resilience | Derive fixtures by removing one declared companion/attachment at a time. Expected result is bounded partial recovery plus explicit missing dependency; never call this a live writer test. |
| Compatibility | Decode public prior-build fixtures with current decoder; separately perform authorized writer upgrade and test original/copy histories. Relocate fixture workspace and distinguish discovery changes from content loss. Publish a version-pair matrix. |
| Retention and redaction | Plant only synthetic markers in declared public-content and sensitive-input channels. Compare native retention and explicit export policy separately. A marker intentionally requested as transcript content is not a leak by definition. Publish policy-conformance results, not a universal 'nothing retained' score. |
| Usage and provenance | Attribute messages/model changes, requests, cache units, retries, and aggregation boundaries. Test availability and reconciliation; distinguish provider-reported, estimated, billed, and subscription units. |
| Incremental reading | Repeated observation while writer runs. Measure visibility delay, duplicates, omitted completed events, and consistent snapshots. Polling a database is allowed; a single tail-able file is not required. |
| Efficiency | Report physical bundle bytes, logical payload bytes, cold-start and marginal growth, attachments, WAL, and semantic duplication with precise denominators. Evaluate both full event-history and final-state views; state information lost by every collapse rule. |
| Export and handoff | Evaluate explicit exports against the native bundle as a separate track. Later test cross-agent continuation with fixed tasks and separate model outcomes; do not make it a v1 core gate. |

Privacy has competing useful outcomes: faithful local retention and safe intentional sharing. Neither should be judged solely by how much text is stored. If artifact sanitization changes a scored property, invalidate that measurement or regenerate the synthetic run; do not publish a flattering transformed artifact as raw evidence.

## Metrics, repetition, and reporting

Publish counts and per-run outcomes before rates. For independently observed in-scope events, recovery is matched expected events divided by observed expected events; a zero denominator is unresolved, not 100%. Report unexpected duplicates separately. Tool-pair precision/recall, attributable-event coverage, violated ordering constraints, unresolved joins, missing attachments, and acknowledged-event loss each have explicit units and expected populations.

No current arbitrary byte threshold carries over. Efficiency curves share the same semantic workload and distinguish cold/warm storage. A small incomplete record cannot outrank a faithful record through storage size. Sampling, truncation, and privacy mode are part of configuration identity.

Core families C01-C05 use three repetitions with fresh run IDs; each of C06's three conditions also has three repetitions. Report conditions separately, all outcomes, range, median where meaningful, and exact sample size. Three successes do not establish a reliable long-run failure rate. Confirmation campaigns may increase repetitions under a declared budget, preserving initial failures. Do not bootstrap thousands of within-session events as independent runs. If confidence intervals are added, use the run as the sampling unit and document the method.

Predeclare one retry allowance for infrastructure failures per scheduled run; preserve the failed attempt and stop on recurring auth/runtime failure. Do not retry valid failures to obtain green rows. Changed prompts, permissions, models, or persistence settings create a new configuration result. Optional features are triggered intentionally; omission by the model is not evidence of format absence.

The public report offers a harness/surface summary, artifact-family reference, scenario matrix, evidence status, and release-drift view. It never averages an untested desktop surface into a CLI vendor score. Schema drift flags only trigger review; a field rename is not automatically breakage, and a stable schema is not proof of semantic compatibility.

## Alternatives and tradeoffs

| Alternative | Benefit | Cost or risk | Decision |
|---|---|---|---|
| Broader v0.4 leaderboard only | Fastest visible expansion | Retains weak evidence and architectural bias | Preserve historically, do not make it the new standard. |
| Atlas only | Low execution cost, immediately useful | Documentation does not establish persistence behavior | Ship atlas incrementally alongside conformance. |
| One universal weighted score | Simple headline | Weights hide loss and incentivize denominator gaming | Defer; use profiles and explicit outcomes. |
| Mandatory common vendor schema | Simpler downstream parsing | Adoption burden; erases native distinctions | Use an internal comparison model with native locators. |
| Full task-performance benchmark | Familiar success metric | Duplicates other work and confounds storage with model capability | Exclude from core. |
| Every surface at launch | Broad marketing claim | Large access, automation, and maintenance burden | Eight-surface pilot, wider atlas, staged verified coverage. |
| Private real-history corpus first | Realistic behavior | Publication and independent reproduction blocked | Use synthetic live-generated evidence first; field corpus is separate. |

## Approval boundary

Design documents are the only changes authorized in this phase. Approval of this design enables the implementation roadmap to begin; live collection additionally needs an authorized access and cost envelope. It does not authorize inspecting personal histories, purchasing services, accessing sibling repositories, publishing, pushing, or contacting maintainers. Those actions remain separately controlled by the user's instructions.

The design is complete only after a separate critique pass and incorporation of consequential findings. The overall goal remains active until approved implementation and its required validation are complete.
